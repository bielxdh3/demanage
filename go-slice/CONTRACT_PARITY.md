# Express and Go contract comparison

The hosted `express-go-contract` job validates the exact loopback DSN and `demanage_parity_test` database name before invoking Prisma or importing the Express application. It then compares the real Express `createApp()` application with the Go HTTP server against that disposable PostgreSQL database after applying the checked-in Prisma migrations. Its synthetic users and tags use fixed, namespaced IDs and `.invalid` email addresses. No production or developer database is read or modified.

The contract checks `/health`, successful `/ready`, authenticated expense and income tag reads, plus the read-only `GET /expenses`, `GET /entries`, `GET /cards`, and `GET /piggy-banks` lists. Financial reads are compared first with empty owner data and then with deterministic synthetic fixtures covering descending creation order, exact BRL decimals, nullable scalar fields, custom tags, card/PIX splits, payments, salary holds, salary versions, and receipts. Card cases also compare current commitments and available limits, including a recurring charge that remains billable through its archive date; archived cards stay out of the list. Piggy-bank cases compare transaction-derived balances and the exact `includeArchived=true` option. A second synthetic owner proves isolation, and missing cookies prove the 401 contract. The card and piggy-bank comparisons freeze only the synthetic request clock at `2026-11-01T02:00:00Z` (23:00 on October 31 in São Paulo), so the billing-cycle close and auto-debit month boundary are deterministic; normal Go requests continue to use the system clock. The custom-tag cases retain alphabetical ordering, owner isolation, missing scope, and invalid scope. It compares HTTP status, JSON bodies, and the stable `Cache-Control: no-store` and `Permissions-Policy: camera=(), geolocation=(), microphone=()` headers on each response. `/health.timestamp` is checked for a valid date and then normalized. All fixtures run only against the hosted job's disposable `demanage_parity_test` database; no production database or write route is involved.

Go's focused tests also check those stable headers with the Express-style JSON content type, ETag, and `X-Powered-By` response behavior. This contract job does not relax any existing CI gate.

The dedicated hosted workflow runs `pnpm test:go-contract:qualify` after building the Go binary and applying migrations to `demanage_parity_test`. It retains the existing 100-request-per-implementation smoke at concurrency 10, then warms both implementations with 100 requests each at concurrency 10 and measures 10 sequential 1,000-request batches per implementation, alternating which implementation goes first. The qualification logs runner OS/architecture, p50, p95, error totals, and the fixed limit; it fails unless both error totals are zero and Go p95 is at most 1.10 times Express p95. These synthetic results qualify only this hosted runner and are not production performance claims. The previously verified PR #147 smoke (100 requests per implementation) reported p95 92.40 ms for Express and 20.13 ms for Go with zero errors; that bounded smoke is not a full benchmark or a general performance claim. `pnpm test:go-contract` runs only the parity cases.
